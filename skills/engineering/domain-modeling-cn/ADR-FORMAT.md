## ADR 格式

ADR 存放於 docs/adr/ 目錄，並採用連續編號：0001-slug.md、0002-slug.md 等。
僅在第一份 ADR 需要建立時，才延遲建立 docs/adr/ 目錄。

### 範本

```
# {決策的簡短標題}

{1 至 3 句：背景脈絡是什麼、做了什麼決策，以及為什麼如此決定。}
```

就這樣。ADR 可以只有一個段落。其價值在於記錄「曾經做出這項決策」以及「做出此決策的原因」，而不是為了填寫固定章節。

### 選用章節

僅在確實能增加價值時才加入。大多數 ADR 都不需要這些章節。
- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）— 適用於決策後續可能被重新檢視或修訂的情況
- **Considered Options**（考慮過的方案）— 僅當被否決的替代方案值得保留時才加入
- **Consequences**（影響與後果）— 僅當需要特別說明不明顯的後續影響時才加入

### 編號規則

掃描 `docs/adr/` 目錄中現有 ADR 的最高編號，並遞增一號。

### 何時應提出 ADR

以下三項條件必須同時成立：
- **難以回復** — 未來若改變主意，所需付出的成本相當可觀
- **若缺乏背景會令人困惑** — 未來的讀者看到程式碼時，會疑惑「為什麼要用這種方式實作？」
- **源於真實權衡取捨** — 確實存在多個可行方案，而你基於特定理由選擇其中之一

如果決策很容易回復，就不必寫 ADR，因為之後直接改回即可。如果決策本身不令人意外，也不會有人質疑其原因。如果根本沒有合理替代方案，那除了「我們採用了最顯而易見的做法」之外，也沒有額外內容值得記錄。

#### 符合條件的事項

- **架構形態（Architectural shape）**。例如：「我們採用 Monorepo。」「寫入模型使用 Event Sourcing，讀取模型投影至 Postgres。」
- **限界上下文之間的整合模式**。例如：「Ordering 與 Billing 透過 Domain Event 溝通，而非同步 HTTP 呼叫。」
- **具有長期綁定成本的技術選型**。例如資料庫、訊息匯流排、身分驗證提供者、部署平台。並非所有函式庫都需要記錄，僅限於那些更換成本可能高達一整季工作的選項。
- **邊界與範圍決策**。例如：「Customer 資料由 Customer Context 負責擁有與管理；其他 Context 僅能透過 ID 參考。」明確定義哪些事情『不能做』，其價值往往與『能做什麼』一樣重要。
- **刻意偏離直覺做法的決定**。例如：「因為 X 原因，我們使用手寫 SQL 而非 ORM。」任何合理讀者原本會預期採取相反做法的情況，都值得記錄。這能避免下一位工程師把刻意保留的設計誤認為缺陷而加以『修正』。
- **程式碼中無法直接看出的限制條件**。例如：「因合規要求，我們不能使用 AWS。」「因合作夥伴 API 合約要求，回應時間必須低於 200ms。」
- **不明顯的被否決方案**。若你曾經評估 GraphQL，最終基於細微但重要的原因選擇 REST，應將其記錄下來；否則六個月後很可能又有人再次提出 GraphQL。
