一個模糊的想法出現了——它太龐大，無法在單一代理工作階段中完成，而且籠罩在迷霧之中：從現在所在之處通往**目的地**的路還看不清楚。Wayfinding 的目的，是找出這條路，而不是直接衝向目的地。這項技能會在儲存庫的議題追蹤器上繪製一張**共享地圖**，接著逐一處理其中的**決策票**——也就是那些需要透過作出決定來解決的問題，而不是可以直接執行的建置工作切片——直到路線清晰為止。

每項工作的目的地都可能不同，而為目的地命名，是繪製地圖的第一個動作；它會形塑後續每一張票。目的地可能是一份要交接並反覆迭代的規格、一項在開始規劃前必須定案的決策，或是一項直接在現有系統中完成的變更，例如資料結構遷移。這張地圖與領域無關——工程工作、課程內容，或任何符合這種形狀的工作都可以。

## 規劃，而不是執行

Wayfinder 預設是用來**規劃**的：每張票都要解決一項決策，而當路徑已經清楚——在有人動手做之前，已經沒有任何事情需要決定——地圖就算完成。人們想直接開始做工作的衝動，通常正代表你已經走到地圖的邊界，是時候交接給執行者了。某項工作可以在其 **Notes** 中明確覆寫這項預設，將執行工作也納入地圖本身；但在沒有這項設定時，請產出決策，而不是交付成果。

## 以名稱引用

每張地圖和每張票都是一個議題，因此都有一個**名稱**——也就是標題。在人類會閱讀的所有內容中——包括敘述文字，以及地圖的「目前決策」——都應以名稱引用它，絕不要只使用裸露的 ID、編號或 slug。滿頁的 `#42、#43、#44` 讓人難以閱讀；名稱則能讓人一眼看懂。ID 和 URL 不會消失——名稱會包住它所連結的內容——但它們應該位於名稱之內，而不是取代名稱。

## 地圖

地圖是此儲存庫議題追蹤器上的單一議題，標籤為 `wayfinder:map`——它是正式且具權威性的產物。地圖中的票是地圖的子議題。

地圖是**索引**，不是資料儲存區。它列出已作出的決策，並指向存放詳細內容的票；每項決策只存在於一個地方——它所屬的票中。因此，地圖不會重述決策，只會提供簡短摘要並附上連結。

**地圖、子票、阻塞關係，以及前沿查詢實際上如何儲存，取決於所使用的追蹤器。** 你應該已經取得議題追蹤器的資訊——如果沒有，請執行 `/setup-matt-pocock-skills`。請查閱追蹤器文件中的「Wayfinding operations」章節，了解**這個**儲存庫如何表達這些操作。如果沒有提供任何追蹤器，預設使用本機 Markdown 追蹤器。

### 票 Tickets

每張票都是地圖的**子議題**；追蹤器的議題 ID 是它的識別身分。票的本文內容是一個問題，其規模應適合單一、最多 100K token 的代理工作階段：

```
## Question

<這張票要解決的決策或調查問題>
```

每張票都帶有一個 `wayfinder:<type>` 標籤，類型可為 `research`、`prototype`、`grilling-cn` 或 `task`（請參閱[票的類型](https://www.perplexity.ai/search/870d4811-11fd-424d-9741-514597c70529#ticket-types)）。

一個工作階段會先將票指派給負責推動此地圖的開發者，以此**認領**該票，然後才開始任何工作，讓並行的工作階段能跳過它。該受指派者就是認領狀態本身：一張開放且未指派的票，代表尚未被認領。

阻塞關係使用追蹤器原生的相依性關係——這一點十分重要，因為它會在追蹤器自己的介面中以視覺方式呈現前沿，讓人不必打開地圖，就能看見哪些工作可以接手。只有在追蹤器不支援原生阻塞關係時，才退回使用本文慣例。一張票在所有阻塞它的票都已關閉時，才算是**未受阻塞**；**前沿**則是所有開放、未受阻塞且未被認領的子票——也就是目前已知範圍的邊界。

答案不會放在票的本文中，而是在解決票時記錄（請參閱[處理地圖](https://www.perplexity.ai/search/870d4811-11fd-424d-9741-514597c70529#work-through-the-map)）。處理票時建立的資產，應從議題連結出去，而不是直接貼在議題內。

## Ticket Types

每張票都屬於 **HITL**——有人在迴路中，由一位代表自己發言的人類共同處理——或 **AFK**——完全由代理獨自推動。HITL 票只能透過即時交流來解決；代理絕不能代替人類完成屬於人類一方的工作。（讓自己提出問題、又自己回答問題的 grilling 代理，就是違反這項規則。）

- **Research**（AFK）：閱讀文件、第三方 API，或知識庫等本機資源，以找出某項決策所依賴的事實。透過 `/research` **子代理**解決。當需要目前工作目錄之外的知識時使用。
- **Prototype**（HITL）：製作便宜、粗略且具體的產物，讓對話能在更高的具體程度上進行，例如大綱、粗略方案、stub，或透過 `/prototype` 技能製作的 UI／邏輯程式碼。將原型作為資產連結。當關鍵問題是「應該長什麼樣子」或「應該如何運作」時使用。
- **Grilling**（HITL）：對話。這是預設情況。務必呼叫 `/grilling-cn` 和 `/domain-modeling` 技能。
- **Task**（HITL 或 AFK）：在作出**決策**之前必須完成的手動工作——沒有需要決定、製作原型或研究的內容，但討論會因它而受阻。例如註冊服務以評估其 API、取得存取權限，或搬移資料以查看其形狀。這是唯一一種「確實執行工作，而不是作出決策」的類型；它存在的理由，是解除某項決策的阻塞，而不是交付目的地本身。代理能獨自完成時，就由代理處理（AFK）；否則便將一份精確的檢查清單交給人類（HITL）。工作完成後即算解決；答案應記錄完成了哪些工作，以及之後票件所依賴的任何結果，例如認證資訊的位置、新 URL、資料列數等。

## Fog of war

地圖是**刻意不完整**的：不要繪製你目前還看不見的內容。現有票之外就是**戰爭迷霧**——你可以察覺即將出現的決策和調查，但因為它們依賴尚未解決的問題，所以還無法釘選下來。解決一張票會清除前方的迷霧，讓此時已經能夠明確描述的內容逐步成為新的票；如此逐一進行，直到通往目的地的路徑清楚，且不再有任何票為止。

地圖中的「尚未指定」區段，就是記錄這種模糊視野的地方：寫下可能存在的問題，以及稍後需要重新檢視的範圍。這是朝向目的地、尚未被發現的前沿——其中所有內容都屬於工作範圍，只是還不夠明確，無法建立成票。根據目前能看見的程度，可以寫得很粗略，也可以寫得很完整；對於想了解這項工作方向的協作者而言，它同時也是路標。

**迷霧還是票？** 判斷標準是：你現在能否精確陳述這個問題，而不是你現在能否回答它。

- **建立票的時機**：問題已經清楚——即使它目前受阻、尚未能採取行動，也應建立票。
- **標記為尚未指定的時機**：你還無法如此精確地表述問題。不要預先把迷霧切割成票大小的片段：迷霧比票更粗略，當前沿抵達後，一個區塊可能會發展成數張票，也可能完全不會形成任何票。

「尚未指定」不包括已經決定的內容（目前決策）、已經存在的有效票，以及不屬於範圍的內容（下一節）。

## Out of scope

迷霧只會朝著目的地聚集。目的地會界定範圍，因此超出目的地的工作屬於**範圍外**——它不是迷霧，也不應放在「尚未指定」中。它應該獨立放在地圖的「範圍外」區段：記錄那些你已經有意識地排除在**這項**工作之外的內容。

範圍外的工作永遠不會逐步成為新票——前沿會在目的地處停止。因此，除非重新描繪目的地，否則它不會再次出現；即使重新納入，也應作為一項全新的工作，而不是原工作的延續。

將某項工作排除在範圍外，是界定範圍的行為，不是路線上的一步。如果一張已經存在的票後來被發現位於目的地之外——可能是在繪製地圖時錯誤納入範圍，也可能是解決某項決策後才暴露出來——就應該**關閉它**（關閉的票明確不會位於前沿），並在「範圍外」區段留下簡短說明：摘要、排除原因，以及指向該已關閉票的連結。它不應出現在「目前決策」中，因為該區段記錄的是實際走過的路線；範圍邊界不是路線上的一步。

## Invocation

共有兩種模式。無論採用哪一種，**每個工作階段都絕不能解決多於一張票**——研究票除外。

### 繪製地圖

使用者以一個模糊的想法發起流程。

1. **命名目的地。** 執行一次 `/grilling-cn` 和 `/domain-modeling` 工作階段，明確確認這張地圖要找出的究竟是什麼——規格、決策，還是變更。目的地會決定範圍，因此必須先定案。
2. **繪製前沿。** 再次進行 grilling，但這次採用**廣度優先**：橫向展開整個空間，而不是深入任何單一脈絡，找出尚未解決的決策，以及目前可以採取的第一步。**如果這次沒有發現任何迷霧**——也就是通往目的地的路已經清楚，整段旅程小到可以在單一工作階段完成——就不需要建立地圖。停止流程，詢問使用者希望如何繼續。
3. **建立地圖**（標籤為 `wayfinder:map`）：填寫 Destination 和 Notes，讓 Decisions-so-far 保持空白，並在 **Not yet specified** 中勾勒出迷霧。
4. **建立目前能夠指定的票**，將它們設為地圖的子議題；接著在第二輪操作中建立阻塞關係（必須先取得議題 ID，才能互相引用）。建立阻塞關係後，票會被區分到前沿或受阻區域；目前還無法指定的內容則全部留在 **Not yet specified** 中。
5. **啟動研究子代理。** 對於剛建立的每一張 `research` 票，平行啟動一個 `/research` 子代理來解決，並將其發現記錄在暫時性的 `research/<name>` 分支上，同時從票中加入上下文指標。
6. 停止——繪製地圖就是一個工作階段的工作；不要在此階段手動解決任何票。

### 處理地圖

使用者以地圖的 URL 或編號發起流程。票是可選的——如果使用者沒有指定，就由你選擇下一項決策，而不是由使用者選擇。

1. 載入**地圖**——只載入低解析度檢視，不要載入每張票的本文。
2. 選擇票。如果使用者指定了某張票，就使用它；否則依序選擇第一張前沿票。**認領它**：在進行任何工作之前，先將它指派給自己。
3. 解決它——視需要深入查看：按需取得相關票或已關閉票的完整本文；呼叫 `## Notes` 區段中指定的技能。如有疑問，使用 `/grilling-cn` 和 `/domain-modeling`。
4. 記錄解決結果：將答案作為**解決結果留言**發布，關閉該議題，並在地圖的 Decisions-so-far 中附加一個上下文指標。
5. 新增新發現的票（先建立，再建立阻塞關係）；將答案已使其變得明確的迷霧內容轉為新票，並從 **Not yet specified** 中移除每個已畢業的區塊，使它只存在於對應的新票中。如果答案顯示某張票——無論是目前這張，還是另一張——其實位於目的地之外，就應將它排除在範圍外，而不是在路線上解決它。如果這項決策使地圖的其他部分失效，請更新或刪除那些票。

使用者可能會平行處理未受阻塞的票，因此要預期其他工作階段會同時編輯追蹤器。
